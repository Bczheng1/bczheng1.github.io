1.CCriticalSection类

然后我们来解决一些其他的问题，在db.cpp中，我们看到有一些这样的代码：

  1. static CCriticalSection cs_db;
  2. ....
  3.  
  4.  
  5. CRITICAL_BLOCK(cs_db)
  6. {
  7.   代码....  
  8. }

定义一个CCriticalSection对象，然后CRITICAL_BLOCK(cs_db)，在大括号里再写代码。

它的用法就是这样。

这个起到什么作用呢？

这个是为了应对多线程，就是里面的共享数据，怕同时被多个线程读写执行，而导致数据混乱。

用了这个线程锁，能保证同一时间只有一个线程执行。

它的实现原理我们来看一下：

  1. // Wrapper to automatically initialize critical section
  2. // Could use wxCriticalSection for portability, but it doesn't support TryEnterCriticalSection
  3. class CCriticalSection
  4. {
  5. protected:
  6.     CRITICAL_SECTION cs;
  7. public:
  8.     char* pszFile;
  9.     int nLine;
  10.     explicit CCriticalSection() { InitializeCriticalSection(&cs); }
  11.     ~CCriticalSection() { DeleteCriticalSection(&cs); }
  12.     void Enter() { EnterCriticalSection(&cs); }
  13.     void Leave() { LeaveCriticalSection(&cs); }
  14.     bool TryEnter() { return TryEnterCriticalSection(&cs); }
  15.     CRITICAL_SECTION* operator&() { return &cs; }
  16. };

运行

看到EnterCriticalsSectgion和LeaveCriticalSection这些函数了吗，这是标准windows api函数，说明底层也是调用api形成互斥锁来实现的。

而CCriticalSection对这些api进行了简单的封装。

里面的CRITICAL_SECTION 是一个结构体（struct），一个api相关的数据类型。

用来实现线程互斥的数据结构。关于这里的api怎么使用，这里不介绍了。不懂的可以查询一下api手册。

接下来我们来看下面的一个类：

2.双for侦测break异常

然后我们来看两个for语句：外层for(后注：这种设计第一个for必定只会执行一次，但有两种情况发生，一种是break打断，只执行一次，一种是正常结束，然后fcriticalblockonce赋值为假也一次结束)

  1. for (bool fcriticalblockonce = true; 
  2.      fcriticalblockonce; 
  3.      assert(("break caught by CRITICAL_BLOCK!", !fcriticalblockonce)), 
  4.      fcriticalblockonce = false)
cpp
运行

外层for在干什么？给fcriticalblockonce初始值为真，然后判断fcriticalblockonce为假就跳出循环，接着开始循环执行一次代码，结束后，执行第三个表达式，判断fcriticalblockonce是否为真，如果为真则报错，并输出提示break caught by CRITICAL_BLOCK。退出循环，如果为假则给fcriticalblockonce赋值为假，接着第二个表达式判断fcriticalblockonce为假，也退出循环。

为什么要这样做呢。

不管怎么样for都只执行一次代码，但退出分为两种情况，一种是输出"break caught by CRITICAL_BLOCK",一种是不输出。

也就是说在fcriticalblockonce在初始被赋值为真后，执行一次代码后，没有break后就会被赋值为假。那么此时是正常的退出，而如果for循环退出后，发现fcriticalblockonce还是为真，则表明异常退出。

但是这个是怎么实现对fcriticalblockonce的值控制呢？是手动写吗？但我们自己使用的时候，没看到有手动写这个fcriticalblockonce值啊。

你们看第三个表达式不是给它赋值为false了吗，如果程序正常结束的话，不用break的话，会执行第三个表达式。

但是后来我一想，如果用break，assert也同样不会执行啊。

然后我测试了：

  1.    for (bool fcriticalblockonce = true; fcriticalblockonce; assert(("break caught by CRITICAL_BLOCK!", !fcriticalblockonce)), fcriticalblockonce = false)
  2.    {
  3.        break;
  4.    }
cpp
运行

确实不会触发，难道我理解错了，这个代码的功能并不是这个，但是我看相关的说明：

  1. // WARNING: This will catch continue and break!
  2. // break is caught with an assertion, but there's no way to detect continue.
  3. // I'd rather be careful than suffer the other more error prone syntax.
  4. // The compiler will optimise away all this loop junk.
cpp
运行

确实是想实现这个功能，不过好像不起作用。

先不管了，我们来看宏定义里的第二个for语句：

for (CCriticalBlock criticalblock(cs); fcriticalblockonce && (cs.pszFile=__FILE__, cs.nLine=__LINE__, true); fcriticalblockonce=false, cs.pszFile=NULL, cs.nLine=0)

运行

然后我帮它简化了一下，并验证了我的猜想：

  1.    for (bool fcriticalblockonce = true; fcriticalblockonce; assert(("break caught by CRITICAL_BLOCK!", !fcriticalblockonce)), fcriticalblockonce = false)
  2.    {
  3.        for (int i=0; fcriticalblockonce ; fcriticalblockonce = false)
  4.        {
  5.            break;
  6.            i = 100;
  7.  
  8.        }
  9.

运行

这次侦测到了break,触发了assert，把break去掉，则正常，不会触发。

原理就是第二层for如果正常结束，就会将 fcriticalblockonce = false，如果用break，非正常退出，则不会执行第三个表达式。然后在上一层for语句判断。

而我们的宏定义，外层封装，导致你的代码不可能写在第一层for里，使用那个宏后，你的代码必定是出现在第二层的for里面的，保证了这个侦测break功能实现。

这个双for的设计，都只执行一次，不是为了循环，主要是为了侦测break。(后注：说实话，不太喜欢这种写法，难以理解，突破了for的正常用法，使阅读变得的困难，调试也麻烦，虽然感觉很酷，富有想象力，但是推荐更现代的写法，现在也不差这点性能资源，可以牺牲一点效率）

还有就是逗号表达式：fcriticalblockonce && (cs.pszFile=__FILE__, cs.nLine=__LINE__, true)

获取一下__FILE__和__LINE__这个是 编译器 内置宏，__FILE__指明了当前代码所属文件名(带路径),__LINE__指明当前代码所在行数，这个是调试用的，出错的时候能快速定位到代码位置。否则只有报错，你不知道出在哪里。比如死锁，你就知道是哪部分代码。因为CRITICAL_BLOCK(cs_db)用的地方很多，可不止这一个。

逗号表达式返回的是最右边的那个值，所以总是true，这里只为执行一下赋值语句。

3.for实现线程锁

我们来看这一句：

  1. CRITICAL_BLOCK(cs_db)
  2. {
  3.     // 用户的代码在这里……
  4.     DoSomething();
  5.    
  6. }
cpp
运行

这个是怎么实现线程锁的呢，对于大括号里的代码。

正常那个api的用法，不是代码开始处加上EnterCriticalSection(pcs),

结束处加上 LeaveCriticalSection(pcs)实现，这里并没有这种写法啊。

这里是利用了for语句的特性来实现的，即for循环开始会执行第一个表达式，我们在这里这定义一个对象CCriticalBlock criticalblock(cs)。

而这个对象的构造函数会开始执行EnterCriticalSection(pcs)，当这个for的作用域结束时，局部变量被释放，那么又会调用这个对象的析构函数执行 LeaveCriticalSection(pcs)。所以{}里的代码，可以看成是被Enter和Leave包裹的。

这种编写一个类，然后利用对象的作用域，通过构造和析构函数实现自动管理的方法，有一种专门的称呼，叫RAII机制。它不仅可以用在线程锁，还可以应用在内存分配与释放上面，以及文件资源管理等需要的地方。

(感觉for语句应该拿来干循环相关的事。不然一门语言都乱套了，for不像for，if不像if，这里的RAII实现同样推荐更现代的写法，C++ 11及以上可以用mutex库里的标准写法，当然那个年代没有相关的功能，当年用for算是一种很好的解决方法吧，现在也不是不能用，如果你个人比较喜欢这种用法的话，初懂这种用法感觉打开了思路，耳目一新，还能这样用。好处也算有吧，加深了对for的理解吧，但是不懂的时候感觉莫名其妙，这都是些什么啊....)

当然如果封装好使用是没问题的，底层翻译成机器码，什么跳转指令啊，其实都一样。

比如最后这样(所以上面说的只是对没封装好的，需要接触底层代码的情况。如果你不需要了解底层代码，能直接就懂了这种用法，也不需要你动底层代码啥的。你就不会有这方面的困扰，可以无视我的看法）：

  1. CRITICAL_BLOCK(cs_db)
  2. {
  3.     // 用户的代码在这里……
  4.     DoSomething();
  5.    
  6. }
cpp
运行

直接这样用，大括号里的代码就是线程锁的代码，然后需要先定义一个CCriticalSection的对象，这里为什么每一段都是定义不同的对象呢？是因为，比如A代码同时只能被一个线程执行，B代码同时只能被一个线程执行，但如果你使用的是同一个对象，那么就是ab代码只能同时被一个线程执行，a代码被锁了，b代码也用不了。看你自己的需要吧。一般没这么复杂的同步，最好也不要这样设计。可以把代码写在一起，然后单独分开线程锁的。

5.头文件包含说明：

注意，这里在main.cpp中尽量把windows.h放在util.h前面，否则可能会有一些问题。这不是一个好的方法，正确的做法是哪个文件依赖的头文件，就在哪个文件里包含就可以了。

我为什么这样说呢，像这种情况，比如有a.h依赖于b.h，你在main.cpp可以这样做：把a.h放在b.h后面。

  1. #include "b.h"
  2. #include "a.h"
cpp
运行

但是如果a.h和b.h互相有依赖呢，此时谁放在前面都可能会容易引起一些错误（根据实际代码而论）

正确的做法，是在a.h中包含b.h b.h包含a.h。但是这样做，不会有嵌套灾难吗？

我们只需要在头文件前面加一这一句：(表明我这个头文件只能被包含一次）

#pragma once
cpp
运行

编译器识别后，只替换一次，头文件就是编译器进行简单替换。有了这个命令后，如果一个cpp，有两次包含这个头文件，那只生成一次。当然这个只是针对单个cpp，不影响另一个cpp，但是如果比如，b.cpp包含a.h头文件，然后a.cpp这样写：

  1. #include "a.h"
  2. #include "b.cpp"
cpp
运行

你不必担心，你只需要记得#pragma once只会有一次头文件包含就行了，b.cpp那里的a.h并不会被包含进来，会被pass掉。

当然包含cpp，几乎没人会这样做，我这里只是说明一下现象，通过它。

回到正题，我在上面为什么不在util.h里包含头文件呢，因为我在bitcoin源码中也没见到，我这里这样写只是为了贴合源码。但是这里给我造成了一些困扰，所以总结了一下。

  1. string GetAppDir()
  2. {
  3.     string strDir;
  4.  
  5.     // 优先级1：如果用户通过命令行参数 -datadir= 手动指定了目录，则直接使用
  6.     if (!strSetDataDir.empty())
  7.     {
  8.         strDir = strSetDataDir;
  9.     }
  10.     // 优先级2：大多数 Windows 系统都会有 %APPDATA% 环境变量
  11.     // 这是推荐存放用户应用数据的标准路径
  12.     else if (getenv("APPDATA"))

  15.         strDir = strprintf("%s\\Bitcoin", getenv("APPDATA"));
  16.     }
  17.     // 优先级3：备用方案（老版本 Windows 可能没有 %APPDATA%）
  18.     // 尝试从 %USERPROFILE% 下构造 Application Data 目录
  19.     else if (getenv("USERPROFILE"))
  20.     {
  21.         // 构造类似 C:\Users\用户名\Application Data 的路径
  22.         string strAppData = strprintf("%s\\Application Data", getenv("USERPROFILE"));
  23.         
  24.         // 静态变量，只执行一次：创建 Application Data 目录（如果不存在）
  25.         static bool fMkdirDone;
  26.         if (!fMkdirDone)
  27.         {
  28.             fMkdirDone = true;
  29.             _mkdir(strAppData.c_str());
  30.         }
  31.         
  32.         // 最终路径为：...\Application Data\Bitcoin
  33.         strDir = strprintf("%s\\Bitcoin", strAppData.c_str());
  34.     }
  35.     // 优先级4：兜底方案，什么环境变量都拿不到时
  36.     // 返回当前工作目录（程序启动所在的目录）
  37.     else
  38.     {
  39.         return ".";
  40.     }
  41.  
  42.     // ====================== 目录创建逻辑 ======================
  43.     // 无论上面走哪条分支，只要成功拿到 strDir，就在这里创建 ...\Bitcoin 文件夹
  44.     // 使用 static 变量保证整个程序运行期间只创建一次
  45.     static bool fMkdirDone;
  46.     if (!fMkdirDone)
  47.     {

这段代码的意思，如果程序代码中指定了数据库目录，即strDir有效，则把目录设置在指定的位置里面。

如果没有，则将数据库创建在用户的公共数据目录下，通过getenv获取到APPDATA环境变量，一般这个环境变量绑定的是C:\Users\用户名\AppData\Roaming\ 之类的。你们可以自行输出检测一下。

这两个路径获取到其中一个后，就会调用_mkdir在该路径下创建一个Bitcoin文件夹，就是创建目录的意思。

如果都没成功获取到呢？直接返回.  那么目录就变成.\，也就是说在当前程序所在目录下创建。
